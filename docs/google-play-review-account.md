# Google Play demo access

Use a dedicated Email/Password member account for Google Play review. Enrollment is tied to its Firebase UID by a server-managed `appReviewAccounts/{uid}` document. It is never selected by email, a client flag, a build flavor or reviewer detection. The regular production app shows the same member screens, clearly labeled as sample data. Public website listings remain real.

## Activate the account

Deploy the Firestore rules and backend from this PR, then build the Android app from the same commit. Create the user in Firebase Authentication first. Run from the repository root after `npm --prefix functions run build`, using operator Application Default Credentials (`gcloud auth application-default login`) or an ignored service-account credential file with Firebase Auth user-management and Firestore data permissions:

```powershell
node scripts/admin/review-account.cjs --project=pluto-9b6ca --uid=NCTYQ7rapWZ6zdd7xqHgCdK26tC2 --email=play-review-1596f6@pluto.events --action=enroll
```

The command confirms the exact UID/email, rejects admin/staff/custom-claim accounts, seeds only the isolated account namespace, and marks the email verified so no inbox access is needed. Running enrollment again preserves existing demo state and does not re-enable a disabled account. Passwords are managed in Firebase Authentication and must never be committed to the repository. Existing builds do not have the new client namespace support; provide Google the updated app build.

If you already signed in with `gcloud auth login` but have no ADC credentials, append `--gcloud`. This uses a short-lived token from that operator login in memory and does not save or print it.

To disable or restore demo access, run the same command with `--action=disable` or `--action=enable`. Leave the enrollment document present when disabling it; deleting it would return the account to ordinary member behavior. Backend operations and Firestore rules enforce disabled access. For permanent account deletion, disable it, recursively delete `appReviewAccounts/{uid}` (including subcollections), delete any normal `userProfiles/{uid}` created before enrollment, and delete the Auth user. Follow the existing account-deletion request process if the owner requests this.

For a staging demo account, create a separate staging Auth user and use its UID/email with `--project=pluto-staging-92eb7`. Do not copy a production UID into staging.

## Paste into Play Console → App access

Provide the account email and password in the credential fields. Instructions:

> Sign in using Email/Password. This is a clearly labeled demo member account using the normal production app interface. No verification code or real purchase is required. Home contains two sample events; tap one to view its details and sample ticket. Tickets contains sample admission and a confirmed RSVP. Tap the QR to enlarge it, and use Orders to inspect sample orders. These QR codes cannot grant real admission. Rewards supports sample redemption, and Profile shows sample points history and editable profile details. In the menu, open Scan QR Code and enter PLUTO-REVIEW to claim a sample scavenger-hunt reward once per account. Open Demo guide to refill sample points whenever needed. Live checkout, email delivery, ticket transfers and event administration are intentionally unavailable for this demo member identity. Public website links display actual event availability. Account deletion instructions are available from Profile.

Keep the credentials working for subsequent reviews. No automatic expiry is set. Sample event dates roll forward to stay visible, and sample reward inventory is unlimited. Refills affect only sample balances. One-time scavenger-hunt claims intentionally keep their normal duplicate protection; subsequent attempts show “already claimed.”

## Isolation and limitations

Demo profiles, points, rewards, claims and redemptions live under `appReviewAccounts/{uid}`. Sample tickets/orders/events are generated by the authenticated backend and are never written to live collections. Every ticketing API request from an enrolled identity is intercepted before live operations or scanner access. Disabled accounts fail closed. Reward transactions check enrollment inside the transaction and preserve normal idempotency. Demo claims use `demoClaims` so real admin collection-group claim reports do not include them.

Demo QR payloads start with `pluto-review:` and are never signed with production ticket keys. This experience does not exercise Stripe, email, transfer or live staff operations; those remain covered by staging tests. No admin privileges are granted. This is member app review access, not organizer access.
